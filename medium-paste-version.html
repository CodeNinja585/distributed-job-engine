Retries, Backoff, and Dead-Letter Queues: What I Learned Building a Job Engine From Scratch

Six weeks, Node.js, BullMQ, and Redis — and the failure modes that only show up once you stop trusting the happy path.

Every job queue lies to you twice

The first lie is silence.

You submit a batch of 50,000 records. The API returns 202 Accepted. The dashboard eventually flips to complete. Three days later someone in finance asks why 340 records never made it downstream.

Nothing crashed. No alert fired. The failure happened inside a worker, inside a callback, and the only thing that noticed was a log line nobody was reading. Data loss is rarely loud. Most of the time it looks exactly like success.

The second lie is enthusiasm.

A downstream provider starts timing out. Your workers do what feels like the responsible thing and retry. So now every job is retrying — immediately, in a tight loop, all of them at once. When the provider finally recovers, it comes back up into a wall of your traffic and falls over again.

This time it's your fault. You've built a denial-of-service and aimed it at your own infrastructure. That's a retry storm, and the ugly part is that it's caused by error handling, not by the absence of it.

I spent six weeks building a distributed job-processing engine from scratch — one vertical slice a week, each with an explicit definition of done before I let myself move on. Not because the world needs another queue; BullMQ already exists and is excellent. I built it because the semantics of failure are the part you only really understand after you've had to implement them yourself.

This is what I learned.

The shape of the system

Before any code, it helps to see what the thing actually is.

   client
     │
     │  POST /jobs          ← returns immediately with a job id
     ▼
  ┌────────────┐
  │  producer  │  splits large work into fixed-size chunks
  └─────┬──────┘
        │  fan-out
        ▼
  ┌──────────────────────────────┐
  │        Redis (BullMQ)        │
  │   jobs  ·  jobs-dead  ·      │
  │   per-batch results + counter│
  └───┬────────┬────────┬────────┘
      │        │        │        ← independent worker processes
      ▼        ▼        ▼
   worker    worker   worker
      │        │        │
      └────────┴────────┘
           fan-in
      (atomic completion)

The API never does the work. It accepts the job, hands back an ID, and returns — an asynchronous status contract. The client polls or subscribes for the outcome. Large jobs get split into chunks that fan out across separate worker processes, then fan back in when every chunk has reported.

That diagram looks simple. It hides four questions, and the happy path answers none of them:

  1. Durability — if this process dies right now, does the job survive?
  2. Retry policy — if a job fails, when does it run again, and how many times?
  3. Terminal failure — if it is never going to succeed, where does it go?
  4. Aggregation — if it's one of 500 chunks, how does anyone know the batch is finished?

Everything below is one of those four questions wearing different clothes.

"Try again" is not a retry policy

Here's the enqueue path:

// Preventing retry storms by backing off exponentially
await jobQueue.add('chunk', { parentId, index, start, end, ms }, {
  attempts: 3,
  backoff: { type: 'exponential', delay: 1000 }
});

Four lines, two decisions worth defending.

Exponential, not fixed. With a base delay of 1000ms, the retries land at roughly 1s, 2s, then 4s. The point isn't the arithmetic — it's that backing off gives the dependency room to recover. A fixed one-second retry is just polling a broken service at high frequency. It converts your error handling into load, which is precisely how you turn a brief outage into a long one.

Three attempts, not ten. A retry budget is a product decision disguised as a config value. Every retry consumes a worker slot that healthy jobs need. Three attempts with exponential spacing is enough to ride out a transient blip — a dropped connection, a momentary 503. Beyond that, you're not recovering; you're taking a long, expensive route to the same failure while starving the rest of the queue.

And the honest limitation: exponential backoff on its own does not fully solve retry storms. If 500 jobs fail in the same instant, they all back off by the same amount and retry in lockstep — a synchronized wave, just a politer one. The fix is jitter: randomizing each delay so the wave spreads out. That's the first thing I'd add to this config, and if you're copying this pattern, add it now rather than after your first incident.

The dead-letter queue: designing for the job that will never work

Eventually a job exhausts its attempts. You have exactly three options.

You can drop it — that's the first lie, silence. You can retry forever — that's the second lie, the storm. Or you can move it somewhere you can look at it.

// When a job exhausts its `attempts`, it doesn't disappear.
// It lands here for manual inspection.
const { Queue } = require('bullmq');
const connection = require('./redis');

module.exports = new Queue('jobs-dead', { connection });

Nine lines. It's the least clever code in the system and probably the most important.

The framing that changed how I think about this: a dead-letter queue is not a graveyard, it's an inbox. Its value isn't that failed jobs are stored somewhere — it's that "how many jobs are in jobs-dead?" becomes a question with an answer. An invisible failure becomes a countable number, and a countable number can be alerted on, graphed, and reviewed.

Which leads to the corollary I'd tattoo on a wall somewhere: a dead-letter queue nobody monitors is just a slower way of losing data. If you build the DLQ and never wire it to a dashboard or a threshold alert, you've built a very tidy hole for records to fall into.

The unexpected payoff is diagnostic. The DLQ is where you find out what actually breaks in your system — the malformed payload you never wrote a branch for, the provider that quietly changed a response shape, the encoding edge case that only exists in production data. Mine taught me more about my own assumptions than any test suite did.

Fan-out, fan-in, and the counter that has to be atomic

This is the part most tutorials skip, and it's the part where naive designs quietly break.

A large job isn't one unit of work. You split it into chunks, each chunk becomes its own job, and workers chew through them in parallel across separate processes. Fine. Now answer question four: how does anyone know the batch is done?

The instinctive answer is to count. Keep a counter, increment it as chunks finish, and when it hits the total, finalize.

That instinct breaks immediately, for two reasons.

The first is obvious once stated: separate worker processes don't share memory. A counter in a Node variable is a counter per process. Three workers means three counters, none of which ever reaches the total.

The second is subtler and worse. Even within a single process, or with a naive "read the value, add one, write it back" against a shared store, you have a classic read-modify-write race. Two workers finish at the same moment. Both read done = 4. Both write 5. One completion has evaporated. The batch never reaches its total, and here's the cruel part — nothing errors. No crash, no exception, no alert. Just a job that sits in processing forever until a human notices.

Here's how I handled it:

// This is the secret to fan-out/fan-in.
// Count distinct chunks, not blind increments (redelivery-proof).
async function recordChunkOutcome(parentId, index, outcome) {
  await redis.hset(key(parentId, 'results'), String(index), JSON.stringify(outcome));
  return redis.hlen(key(parentId, 'results')); 
}

// First writer wins
const setFinal = (parentId, obj) =>
  redis.set(key(parentId, 'final'), JSON.stringify(obj), 'NX');

Two things are happening, and both matter.

The hash stores outcome, not status. Each chunk writes its result under its own index. The batch's outcome isn't a boolean — it's a map. I'll come back to why that matters.

INCR is atomic, and it returns the post-increment value to the caller. This is the whole design, and it's worth sitting with. Redis processes the increment as a single indivisible operation, so no two callers can receive the same number. Every worker that finishes a chunk gets a distinct integer back. Which means exactly one caller — ever — sees the value equal to the total chunk count.

That caller, and only that caller, runs finalization.

No locks. No leader election. No "who's responsible for closing out the batch?" ambiguity, and no window where two workers both think they're last. INCR's return value is a ticket dispenser, and the last ticket is unambiguous by construction. The elegance isn't that Redis is fast — it's that the guarantee you need is already in the primitive.

Partial success is a first-class outcome

Because outcomes are stored per index rather than collapsed into a flag, a batch with 3 failures out of 500 is exactly that: 3 failures out of 500. Not a failed batch.

I can report precisely which chunks failed and why. I can retry only those three. The other 497 stand.

The naive design — one boolean for the whole batch — throws away 497 successful chunks because 3 went wrong, then makes someone reprocess all 500 to fix 3. That isn't a performance problem, it's a correctness and cost problem, and it comes entirely from a data-modelling decision made in about ten seconds early on.

The trade-off I had to defend

I presented this architecture internally and got the question I should have expected: why Redis? Leadership pushed on durability and data-loss risk compared to a dedicated broker like RabbitMQ.

It's a fair challenge, and it deserves a real answer rather than a defensive one.

RabbitMQ is genuinely better at being a message broker. It's purpose-built, with guaranteed delivery via acknowledgments and durability semantics that are its entire reason for existing. That's not a point I wanted to argue away.

The cost is operational. Running RabbitMQ means running and maintaining an Erlang-based cluster — a second piece of stateful infrastructure to monitor, upgrade, and reason about — in order to process background jobs.

What BullMQ buys in a Node ecosystem is real. The developer experience is substantially better, and — this is the part people miss — BullMQ leans on Redis Lua scripts to make complex job semantics atomic. Retries, delays, priorities, repeatable jobs: the operations that people assume are racy on Redis are executed as single atomic scripts. The atomicity I depend on isn't accidental.

And the honest cost: Redis is primarily in-memory. In a catastrophic crash without AOF persistence enabled, jobs in flight can be lost. That is a real exposure and I'm not going to dress it up.

I accepted it. Operational simplicity, development velocity, and the ability to reuse existing Redis infrastructure for both caching and queuing outweighed an extreme-edge-case data-loss risk for this specific workload. The optimization was for velocity and simplicity without giving up the atomic guarantees the partial-batch logic actually depends on.

The broader lesson landed harder than the technical one. What satisfied the question wasn't insisting Redis was fine. It was being able to name the exact failure mode I was accepting, and why I was accepting it here and might not elsewhere.

An architecture decision you can't state the cost of isn't a decision. It's a default.

What the numbers said — and the one that lied

The worry I went in with was contention. Every chunk in a batch increments the same Redis key — a hot key by construction, and hot keys are where clever designs go to die.

That isn't what the load test found. It found something more useful.

I ran the same workload twice under k6 and changed exactly one variable: worker count. Each job carries a fixed ~500ms of work.

                                   2 workers      8 workers
  p95 queue wait                   60,114 ms           6 ms
  p50 / p95 service time        501 / 502 ms   501 / 502 ms
  API p95 (http_req_duration)         5.52 ms       ~same
  Failed requests                          0%            0%

A full minute of queue wait down to six milliseconds, from a config change.

But the rows that didn't move are the ones worth your attention.

Service time never budged. 501ms saturated, 501ms idle. Once a worker picked up a job it took exactly as long as it always had. The work didn't get slower. There was simply nobody free to start it.

And the API stayed green. http_req_duration p95 of 5.52ms, zero failed requests — the API answered every single call in under six milliseconds while jobs sat in the queue for a full minute. Health checks passing. Response-time graphs flat and healthy. The system was drowning and nothing on the dashboard said so.

That's the lesson worth more than the fix:

Under saturation, latency doesn't degrade — it queues. Service time stays flat while wait time explodes. A system can be failing badly while every response-time graph looks perfect.

And the ceiling isn't a tuning problem, it's arithmetic:

throughput = workers × (1 / service time)

2 workers × (1 / 0.5s) = 4 jobs/sec

Push arrivals above that line and the backlog isn't slow — it's unbounded. No amount of profiling will find it, because nothing is slow. Every individual operation is behaving exactly as designed. You need queue depth and time-in-queue on a graph, or you will not see it coming.

The hot key I'd designed against never surfaced as the limit. Worker capacity did — which is its own reminder that the bottleneck is rarely the one you defended against in review. It's the one you didn't think to measure.

One caveat, because I'd rather be useful than impressive: this characterizes a specific service-time profile at a specific load. Where the atomic counter finally does bite — and what shape that degradation takes — is still an open question, and not one I've earned an answer to yet.

If you're building one of these

Six weeks compressed into six lines:

  • Decide what happens to a permanently-failing job before you write the happy path. Retrofitting terminal-failure handling means retrofitting it into every call site.
  • Backoff without jitter is half a solution. Synchronized retries are still a storm.
  • Never count distributed work in application memory. Use a primitive whose atomicity you can point at in the docs.
  • Model partial success explicitly. A boolean for a 500-chunk batch is a bug you haven't hit yet.
  • A DLQ nobody monitors is just slower data loss. Wire it to an alert the same day you build it.
  • Graph queue depth and time-in-queue, not just response time. A green latency dashboard is not evidence of a healthy system.
  • Be able to state the failure mode you're accepting. Out loud, to someone who'll push back.

A job queue's real product isn't throughput. It's trustworthy answers about what happened — and every one of the decisions above exists to protect that.
